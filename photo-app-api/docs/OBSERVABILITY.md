| Tool | URL | Credentials |
|---|---|---|
| **Zipkin** — trace search | http://localhost:9411 | none |
| **RabbitMQ** — management | http://localhost:15672 | `RABBITMQ_USER` / `RABBITMQ_PASSWORD` from `.env` |

Real passwords live **only** in `.env`, which is gitignored. They are never in this file, never
in the config repo, and never in an image.

`xpack.security` is enabled on Elasticsearch, so Kibana and Logstash both authenticate and both
trust the CA generated by the `photo-app-elk-certs` bootstrap job.

## 2. One-time Kibana setup: the Data View

**Discover shows nothing without this**, even though the logs are in Elasticsearch. It is not a
failure — Kibana simply does not know which indices to read.

Needed **once per Elasticsearch volume**. Restarting containers does not require it; only
destroying `photo-app-es-data` (i.e. `stack.sh down -v`) does.

1. Hamburger menu (☰) → **Stack Management** → **Data Views**
2. **Create data view**
3. **Name / Index pattern:** `photoapp-logs-*`
   The `*` is required — the real index is `photoapp-logs-YYYY.MM.dd` and rolls daily.
4. **Timestamp field:** `@timestamp`
5. **Save data view to Kibana**
6. ☰ → **Discover**, then select `photoapp-logs-*` in the dropdown

Sanity check that documents exist at all, without Kibana:

```bash
docker exec photo-app-elasticsearch curl -s -k -u "elastic:$ELASTIC_PASSWORD" \
  "https://localhost:9200/_cat/indices/photoapp-logs-*?v"
```

## 3. Available log fields

Written by `LogstashEncoder` in every component's `logback-spring.xml`:

| Field | Example value | Notes |
|---|---|---|
| `service` | `photo-app-accounts-service` | Custom field, from `spring.application.name` |
| `environment` | `dev` | Custom field, from `spring.profiles.active` |
| `level` | `INFO` `DEBUG` `WARN` `ERROR` `TRACE` | All five occur |
| `logger_name` | `com.photoapp.security.filter.JwtFilter` | Fully-qualified category |
| `message` | `ACCESS_DENIED path=/accounts message=Access Denied` | Free text |
| `traceId` | `6a6ec2e1db149f838b717634842ddb4b` | 32 hex chars — same id Zipkin uses |
| `spanId` | `7a44f9b408e7baf9` | 16 hex chars — one unit of work inside a trace |
| `thread_name` | `http-nio-8082-exec-9` | Port in the name tells you which service |
| `host.name` | `b8610c0ad160` | Container id, not a hostname you set |
| `@timestamp` | — | The Data View's time field |
| `log.file.path` | `/var/log/photo-app/photo-app-accounts-service/logs/…log` | Added by Logstash |

### `.keyword` vs plain — read this before writing queries

Every string field is indexed twice:

- **`field`** — *analyzed*. Broken into lowercase tokens. Good for partial and word matching.
  `message:ACCESS_DENIED` finds the line because `ACCESS_DENIED` is one of its tokens.
- **`field.keyword`** — *not analyzed*. The whole value, exact and case-sensitive. Required for
  aggregations, sorting, and exact equality.

The practical consequences:

| You want | Use |
|---|---|
| Find a word anywhere in the message | `message:"ACCESS_DENIED"` |
| Exact whole-value match | `service.keyword:"photo-app-users-service"` |
| A visualization / terms aggregation | `.keyword` — the plain field will fail |
| Prefix matching | `message:AUTH*` (analyzed) or `logger_name.keyword:com.photoapp.security*` |

`*` matches zero or more characters. Leading wildcards (`*Service`) work but scan every term and
are slow — avoid on large ranges. A wildcard against an analyzed field matches within a single
token, not across the whole value: `message:ACCESS*` matches, `message:ACCESS_DENIED*path*` does
not.

For `service` and `level` in this project both forms behave the same in practice, because the
values contain no spaces and the analyzed form lowercases them — Kibana's KQL handles the
case-insensitivity for you. Prefer `.keyword` anyway when you mean *exactly this value*.

## 4. Common Kibana queries

Paste into the KQL bar in **Discover** with the `photoapp-logs-*` data view selected. Every
example below uses field names and values verified against this project's live index.

### 1. Everything from one service

```
service:"photo-app-users-service"
```

*Answers:* "what is this service doing right now?" The first thing to run when one service is
misbehaving and you want its story without the other seven interleaved.

### 2. Follow one request across every service

```
traceId:"6a6ec2e1db149f838b717634842ddb4b"
```

*Answers:* "what actually happened during this one request?" This is the single most valuable
query here. One HTTP call to the gateway fans out through several services; this returns every
line all of them logged for that call, and sorting by `@timestamp` ascending gives you the
request in order — gateway → service → Feign call → database → response.

Get the `traceId` from a Zipkin trace, from an error log line, or from any log line at all.

### 3. Narrow to one step inside a trace

```
traceId:"6a6ec2e1db149f838b717634842ddb4b" and spanId:"7a44f9b408e7baf9"
```

*Answers:* "Zipkin says this one span took 800ms — what was it doing?" A trace can hold dozens of
spans; this isolates the one you clicked on in the Zipkin waterfall.

### 4. All problems, everywhere

```
level:"ERROR" or level:"WARN"
```

*Answers:* "is anything wrong at all?" Run this over the last 15 minutes after a deploy or a
config change. In this stack WARN is meaningful — it carries expired JWTs and authorization
denials, not just noise.

### 5. Problems in one service

```
service:"photo-app-accounts-service" and level:"ERROR"
```

*Answers:* "the accounts service is failing — what is it failing on?" Combine with the time
picker to bracket the window when the failures started.

### 6. Authorization denials

```
message:"ACCESS_DENIED"
```

*Answers:* "who is being refused, and on what path?" These lines come from
`GlobalExceptionHandler` at WARN and read
`ACCESS_DENIED path=/accounts message=Access Denied`. Before the Step 8 fix these surfaced as
opaque 500s; they are now a deliberate, greppable 403 signal. A sudden cluster of them means
either a real permission bug or a client sending the wrong token.

### 7. Business events by message text

```
message:"AUTH LOGIN*"
```

*Answers:* "who is logging in, and is login working?" Matches the authorization service's
`AUTH LOGIN started username=admin` lines. The same shape works for any convention-following
message prefix — the wildcard is what lets one query catch `AUTH LOGIN started`,
`AUTH LOGIN success` and any future variant.

### 8. One component's behaviour inside one service

```
service:"photo-app-albums-service" and logger_name:"com.photoapp.security.filter.JwtFilter"
```

*Answers:* "is JWT validation the thing that's failing on albums?" `logger_name` is the class
that emitted the line, so this isolates a single component's contribution. Especially useful for
shared library code like `JwtFilter`, which runs identically in five services — this asks what
it did in *this* one.

### 9. Time bounds plus text

```
service:"photo-app-photos-service" and level:"ERROR" and message:"timeout"
```

The time picker in the top right is an **additional** filter, not an alternative to KQL — the
two always apply together. So the workflow is: set the range to the incident window (*Absolute*
for a known window, *Relative* like "Last 30 minutes" while watching something live), then
narrow with KQL. Widening the range never changes your query; it just gives it more documents.

A frequent mistake is a correct query that returns nothing because the time picker is still on
"Last 15 minutes" and the event was an hour ago. Check the range before concluding the data
isn't there.

### 10. Wildcards and partial matches

```
logger_name:com.photoapp*
```

*Answers:* "show me only our code, not the framework's." The index is dominated by Spring,
Netflix and Hibernate loggers; this filters to application classes.

More of the same shape:

```
service:photo-app-*-service          all five business services, excluding gateway/config/discovery
message:*Feign*                      anything mentioning Feign (slow — leading wildcard)
logger_name.keyword:com.photoapp.commons.exception.GlobalExceptionHandler   exact class
```

Rules worth remembering:

- `*` = zero or more characters; there is no `?` single-character wildcard in KQL.
- Against an **analyzed** field the wildcard applies **within a token**, so
  `message:ACCESS*` works but a pattern spanning the whole phrase does not.
- Against a **`.keyword`** field it applies to the entire value — which is what you want for
  prefix-matching package names.
- A leading `*` disables the index's term optimization. It works, but avoid it over wide ranges.

## 5. The two-way workflow

The point of `traceId` appearing in both systems is that you can start from either.

**Slow request → what was slow:**
Zipkin (http://localhost:9411) → *Run Query* → sort by duration → open the slow trace → read the
waterfall to find which span dominates → copy the trace id → in Kibana run
`traceId:"<id>"` to see what that service was logging at the time.

**Error in the logs → where it came from:**
Kibana → `level:"ERROR"` → open a document → copy its `traceId` → paste into Zipkin's search box
→ see the full call tree, including the services that succeeded before the failure.

Sampling is `management.tracing.sampling.probability=1.0`, so **every** request is traced. That
is correct for a dev stack and would need lowering under real load.

## 6. Troubleshooting

**Discover is empty.**
In order: (1) is the Data View created and selected? (2) is the time picker on a range that
contains your data? (3) do the indices exist — `_cat/indices` above? (4) is Logstash running —
`docker compose ps logstash`?

**Logs stop appearing after a restart.**
Logstash tracks its read position in a sincedb on the `photo-app-logstash-data` volume. That is
deliberate — without it, every restart re-ingests every file from the beginning and duplicates
every document. If you genuinely need a re-read, remove that volume specifically, not all of them.

**Nothing from a service you're running in IntelliJ.**
Expected. Logstash tails the `photo-app-logs` Docker volume; a natively-run service writes to
your host filesystem, which is not mounted into Logstash. Tracing still works. See
[RUNNING.md](RUNNING.md#known-limitation-native-logs-do-not-reach-kibana).

**Kibana won't authenticate.**
The `photo-app-elk-users` job sets the built-in passwords from `.env`. If `ELASTIC_PASSWORD`
changed after the volume was created, the stored password is the old one — the job sets it at
bootstrap, it does not reconcile on every start.

**A trace shows only one service.**
The others didn't report spans. Check that the component has `photo-app-tracing-lib` on its
classpath: Boot 4's default JDK-HttpClient sender fails in these containers with
`ClosedChannelException`, and that library is what replaces it.
