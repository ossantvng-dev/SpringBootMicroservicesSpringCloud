[2026-08-01 | reported] HIGH — 500 for authenticated non-admin users on protected
endpoints                                              [UNVERIFIED - NOT REPRODUCED]
------------------------------------------------------------------------------------
STATUS: reported by Oscar. NOT observed, reproduced or diagnosed by any work in
Steps 1-6, and no earlier backlog entry described it — this entry is being created
from Oscar's report, not from a measurement. Recorded now so the eventual
investigation starts warm.

Symptom as reported: a user who authenticates successfully but lacks the required
role gets HTTP 500 on a protected endpoint, instead of 401/403.

Why it is plausible and untested: every verification run in Steps 1-6 used a
hand-minted token carrying scope ["USER","ADMIN"], i.e. always authorised. The
authenticated-but-insufficient-role path was therefore never exercised. Steps 1-6
also changed all three error-handling layers below, so a regression in their
interaction would not have been caught.

FIRST REPRODUCTION STEP (do this before reading further): mint a token with scope
["USER"] only and call an ADMIN-only route. The existing helper is
scratchpad/MintToken.java — change the scope claim. Compare against a token with
["USER","ADMIN"].

Investigation starting points — Oscar's hunch is that the break may be in the
INTERACTION between these layers rather than inside any one of them:

  1. GlobalExceptionHandler (photo-app-commons, @RestControllerAdvice)
     Handles ApplicationException, MethodArgumentNotValidException,
     ConstraintViolationException, DataAccessException, OptimisticLockException
     and a catch-all. Check whether the catch-all is swallowing a more specific
     type that used to be handled correctly, converting it into a generic 500
     instead of the correct 401/403. Note especially that AccessDeniedException
     must NOT be caught by the advice — if it is, Spring Security never sees it
     and cannot translate it to 403.

  2. CustomFeignErrorDecoder (photo-app-feign-lib)
     Maps downstream 401/403/404/503/other into ApplicationException. If a
     non-admin request triggers an inter-service Feign call (e.g. ownership
     validation against another service) and that call's error response is no
     longer decoded into the right exception type, it can surface as an
     unhandled 500 rather than the correct status. CurrentUserService
     .canAccessResource is the ownership primitive to trace.

  3. JWT error handling now that WebMVC is the only chain (Step 1 deleted the
     reactive one). Confirm JwtFilter's handling of a VALID token with
     INSUFFICIENT role — as distinct from expired or malformed, which are the
     only cases verified so far — still reaches the AccessDeniedException path
     and the accessDeniedHandler that returns 403, rather than throwing
     something the generic catch-all turns into a 500.

Cross-check while investigating: Step 1 permitted /error in SecurityConfiguration
precisely because the servlet ERROR dispatch was masking real statuses as 401.
That change moves what the client sees on any error dispatch, so it is worth
confirming it did not convert a would-be 403 into a 500.

Priority: HIGH per Oscar. Not scheduled into a step yet.


[2026-08-01 | Step 1] Gateway: backend-unavailable failures render as 500, not 503
---------------------------------------------------------------------------------
When no instance of a downstream service is registered, the load balancer raises
HttpServerErrorException: 503, which propagates as a servlet exception and the
error dispatch renders HTTP 500. The WebFlux stack surfaced 503 directly.
Only affects the service-unavailable error path. A dedicated exception handler at
the gateway would restore fidelity.
Priority: low.


[2026-08-01 | Step 1] Actuator sub-paths shadowed by Spring Cloud Function's web handler
----------------------------------------------------------------------------------------
Spring Cloud Function's web handler arrives transitively via
spring-cloud-starter-bus-amqp and intercepts /actuator/<sub-path> requests,
turning e.g. /actuator/gateway into
"Failed to lookup function to route based on the value of
'spring.cloud.function.definition' property 'actuator/gateway'".
Pre-existing across all five business services as well — not introduced by the
webmvc migration.
CORRECTION 2026-08-01 (Step 4): the proposed fix was WRONG and has been dropped.
spring.cloud.function.web.enabled=false is a no-op here — spring-cloud-function-web
is not on any module's classpath (only spring-cloud-function-context, pulled in by
spring-cloud-stream-binder-rabbit). Measured on the gateway with and without the
flag, results are identical:
    /actuator/gateway         -> 415   (function lookup error, logged once per hit)
    /actuator/gateway/routes  -> 404
    /actuator/health          -> 200
    /actuator/info            -> 200
The original Step 1 reading was a false inference: the flag was changed in the same
sitting as permitting /error and setting management.endpoint.gateway.access, and the
improvement came from those, not from this flag.
Revised severity: LOW / cosmetic. Real actuator endpoints are never shadowed — only
unmapped /actuator/<x> paths fall through to the function handler and return 415
instead of 404. Since /error is permitted (Step 1) this no longer masks anything as
a 401.
Correct fix: unknown, and not worth chasing now. If the gateway actuator endpoint is
ever actually wanted, start by investigating why it 404s under
spring-cloud-gateway-server-webmvc 5.0.1 even with
management.endpoint.gateway.access=unrestricted.
NOT scheduled — deliberately left open.


[2026-08-01 | Step 2] Wrong/missing config-server credentials degrade silently
------------------------------------------------------------------------------
New failure mode introduced by putting HTTP Basic in front of the Config Server.
With spring.config.import=optional:configserver:..., a 401 is logged as a WARN
("Could not locate PropertySource ... 401") and startup CONTINUES with no remote
configuration at all. Whether the app then fails depends entirely on whether some
bean happens to need a property only the server provides — the gateway does fail,
because JwtClaimsParser requires ${photoapp.jwt.secret}, but that is luck, not a
guard. A component whose remote properties are all optional would boot silently
misconfigured.
Fix: drop the "optional:" prefix so a 401 or an unreachable server is fatal.
Already planned for containers via SPRING_CONFIG_IMPORT in Step 8; consider doing
the same for the packaged properties so native runs fail loudly too.
Priority: medium.


[2026-08-01 | Step 2] Config Server health is DOWN whenever RabbitMQ is down
----------------------------------------------------------------------------
/actuator/health is deliberately left unauthenticated for container healthchecks,
but it aggregates the Rabbit health indicator (Spring Cloud Bus), so it returns
503 DOWN whenever RabbitMQ is unavailable — confirmed during the Step 2 smoke
test. A compose HEALTHCHECK on that endpoint therefore reports the Config Server
unhealthy on any Rabbit blip, and ordering must gate the Config Server on
rabbitmq being service_healthy.
Consider a dedicated health group for the readiness probe that excludes rabbit.
Relevant to: Step 7 (compose infrastructure).
Priority: medium — decide before writing the healthchecks.


[2026-08-01 | Step 3] Config Server's Eureka properties are dead config   [RESOLVED]
------------------------------------------------------------------------------------
RESOLVED 2026-08-01: both properties deleted. Decision — the Config Server is
deliberately NOT registered with Eureka: every client reaches it by direct URL
through spring.config.import, so registering it would only introduce a bootstrap
chicken-and-egg problem for no benefit, since nothing needs to discover it
dynamically. EUREKA_URL is therefore not required by this container and must not
be added to its Step 8 compose environment. Verified by starting the Config
Server with EUREKA_URL unset: clean start, no unresolved placeholder.
Original finding below.

Its application.properties declares
  eureka.client.service-url.defaultZone=${EUREKA_URL}
  eureka.instance.prefer-ip-address=true
but the pom has NO eureka client dependency (grep for "eureka" in it returns
nothing), so the Config Server never registers. Confirmed during the Step 3 run:
Eureka listed six registrations — the five business services plus the gateway —
and no configuration server.
This is harmless in practice because clients reach the Config Server by URL via
spring.config.import, not through discovery. But it means EUREKA_URL is a
required-looking env var that does nothing.
Decide: either add spring-cloud-starter-netflix-eureka-client and register it, or
delete both properties and drop EUREKA_URL from the Step 8 compose environment
for this container. Do not leave it as-is.
Priority: low, but resolve before Step 8 writes the compose env block.

[2026-08-01 | Step 5] Audit remaining DTO/entity name mismatches
----------------------------------------------------------------
The MapStruct migration exposed that AccountDTO.accountTypeDTO never received
Account.accountType under ModelMapper — the API returned null while the database
held PREMIUM. Fixed by an explicit @Mapping.
The naming convention that caused it is still in place: AccountDTO and
CreateAccountInputDTO use the suffixed name "accountTypeDTO" for a field the
entity calls "accountType". Every other DTO field matches its entity field name
exactly, so this is the only current instance, and MapStruct's
unmappedTargetPolicy=ERROR now makes any recurrence a build failure rather than a
silent null.
Consider renaming AccountDTO.accountTypeDTO -> accountType and
CreateAccountInputDTO.accountTypeDTO -> accountType for consistency with every
other DTO. NOTE: this is an API-breaking change, since the field name appears in
request and response JSON. Not done for that reason.
Priority: low. Decide alongside any future API versioning work.
