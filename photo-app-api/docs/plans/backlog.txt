[2026-08-01 | reported] HIGH — 500 for authenticated non-admin users on protected
endpoints                                                   [CONFIRMED AND FIXED]
------------------------------------------------------------------------------------
Reported by Oscar, reproduced, diagnosed and fixed on 2026-08-01.

SYMPTOM: a user who authenticated successfully but lacked the required role got
HTTP 500 "Unexpected error occurred" on an @PreAuthorize-protected endpoint,
instead of 403.

ROOT CAUSE: @PreAuthorize denial throws
org.springframework.security.authorization.AuthorizationDeniedException, which
extends AccessDeniedException extends RuntimeException. It is thrown by
AuthorizationManagerBeforeMethodInterceptor INSIDE the DispatcherServlet, so
GlobalExceptionHandler's @ExceptionHandler(Exception.class) catch-all matched it
first and returned 500. Because the advice handled it, the exception never
propagated out to Spring Security's ExceptionTranslationFilter — the component
that would route AccessDeniedException to the configured accessDeniedHandler.
That accessDeniedHandler in SecurityConfiguration was therefore dead code for
method-security denials; it only ever fired for filter-level
authorizeHttpRequests denials.

NOT A REGRESSION FROM STEPS 1-6. Verified: GlobalExceptionHandler is untouched by
every commit in this session (git log 751d250..HEAD for that file is empty); the
catch-all predates the work (commits 8a81452, e1e98eb); and @EnableMethodSecurity,
accessDeniedHandler and all eight @PreAuthorize annotations already existed at
751d250, the commit before Step 1. This was a pre-existing latent bug, live for as
long as @PreAuthorize and the catch-all had coexisted. It had simply never been
exercised, because every test token used before this point carried scope
["USER","ADMIN"] and was therefore always authorised.

RULED OUT during diagnosis:
  - The Step 1 /error permitAll change is NOT involved. The 500 body carried the
    ApiErrorDTO shape (httpStatus/error/message/path/timeStamp) produced by
    GlobalExceptionHandler.buildResponse, meaning the advice returned a
    ResponseEntity directly and no servlet ERROR dispatch occurred. An ERROR
    dispatch would have produced Spring's default {timestamp,status,error,path}.
  - CustomFeignErrorDecoder is NOT involved. It appeared only in the ADMIN
    request's trace, correctly decoding a genuine downstream 503. A USER-only
    request never reaches Feign; @PreAuthorize rejects it before the controller
    body runs.

FIX: added @ExceptionHandler(AccessDeniedException.class) to GlobalExceptionHandler,
positioned ABOVE the catch-all, returning 403 with the standard ApiErrorDTO body and
logging at WARN (an authorization denial is an expected outcome, not a fault).
Catching AccessDeniedException also covers AuthorizationDeniedException. Required
adding spring-security-core to photo-app-commons — deliberately the core artifact,
not the starter, consistent with the earlier narrowing of that module.

BLAST RADIUS — one fix covers everything. There is exactly ONE @RestControllerAdvice
in the entire codebase, in photo-app-commons. All five services resolve commons
(authorization-service transitively via photo-app-feign-lib) and all five
component-scan com.photoapp.commons. No per-service duplication exists.

VERIFIED after the fix, on two different services and two different endpoints:
  accounts POST /accounts            no token 401 | USER-only 403 | USER+ADMIN 503*
  albums   DELETE /albums/byAccountIds no token 401 | USER-only 403 | USER+ADMIN 404*
  (* the admin results are correct pass-through: a downstream service was not
     running, and account 999 does not exist)
  403 body: {"httpStatus":403,"error":"Forbidden","message":"Forbidden","path":...}
  Denials logged as ACCESS_DENIED at WARN; UNHANDLED_EXCEPTION count zero.


[2026-08-01 | Step 8] No traces reach Zipkin from containers        [FIXED]
---------------------------------------------------------------------------
FIXED 2026-08-01 by replacing the span transport. Boot 4 sends spans through
ZipkinHttpClientSender, built on the JDK java.net.http.HttpClient, which fails
permanently in containers (see root cause below). photo-app-tracing-lib now
publishes a BytesMessageSender backed by URLConnectionSender; Boot declares its
own sender under @ConditionalOnMissingBean(BytesMessageSender.class), so it
backs off. HttpURLConnection was already proven to work in these exact
containers during diagnosis.

The library is registered as an auto-configuration ordered before
ZipkinAutoConfiguration, not as a @Component, because the Config Server and the
Discovery Service do not component-scan any com.photoapp package. It is a new
module because no existing library is shared by all eight deployables - those
two depend on none of them.

The underlying trigger that breaks the JDK client is NOT fixed, only bypassed.
It is tracked as a separate follow-up item below.

Original diagnosis retained:
--------------------------------------------------------------------
Tracing worked in the Step 3 NATIVE run (all eight components reported spans).
In containers it does not: Zipkin receives nothing from any application service.
Everything else in Step 8 verified fine, so this is isolated to span delivery.

WHAT IS RULED OUT (all measured, not assumed):
  - Configuration is correct. /actuator/env with show-values enabled reports
    management.zipkin.tracing.endpoint = http://photo-app-zipkin:9411/api/v2/spans
    sourced from systemEnvironment (origin: MANAGEMENT_ZIPKIN_TRACING_ENDPOINT),
    and management.tracing.sampling.probability = 1.0 from the config server.
  - Spans ARE being created and sampled: the service logs
    "Dropped 37 spans due to ConnectException()" - it has spans to send.
  - The collector is healthy and reachable FROM THE SERVICE CONTAINER:
      curl http://photo-app-zipkin:9411/health            -> 200
      curl -X POST .../api/v2/spans with a hand-written span -> 202,
    and that manual span IS stored and queryable (service "manual-probe-svc"
    appears in /api/v2/services). So DNS, routing and the collector all work.
  - Not a restart-ordering artifact: restarting a single service while Zipkin had
    been stable for minutes still produced 9 drops and no stored spans.
  - Tracing auto-configuration is active: braveTracer and zipkinConnectionDetails
    beans exist; BraveAutoConfiguration, ZipkinAutoConfiguration and
    ZipkinWithBraveTracingAutoConfiguration are all present.

ROOT CAUSE (found 2026-08-01, second investigation pass)
The failure is in the HTTP transport, not in configuration or networking. Full
stack trace from the reporter:

  java.net.ConnectException
    at jdk.internal.net.http.HttpClientImpl.send
    at org.springframework.boot.zipkin.autoconfigure.ZipkinHttpClientSender.postSpans
    at zipkin2.reporter.internal.AsyncReporter$BoundedAsyncReporter.flush
  Caused by: java.net.ConnectException
    at jdk.internal.net.http.PlainHttpConnection.connectAsync
  Caused by: java.nio.channels.ClosedChannelException
    at sun.nio.ch.SocketChannelImpl.ensureOpen
    at sun.nio.ch.SocketChannelImpl.connect

Boot 4 sends spans through ZipkinHttpClientSender, which uses the JDK
java.net.http.HttpClient. The socket channel is ALREADY CLOSED when connect is
attempted - ensureOpen fails before any network I/O happens. That is why the
address is irrelevant and why nothing outside the JVM can observe a failure.

BOTH SUGGESTED LEADS WERE TESTED AND RULED OUT:
  1. IPv4/IPv6 preference - NOT the cause. A probe inside the service container
     shows java.net.preferIPv4Stack unset, "photo-app-zipkin" resolving to a
     single IPv4 address (172.19.0.2, ipv6=false), a successful TCP connect to
     172.19.0.2:9411, and HttpURLConnection returning 200. Adding
     -Djava.net.preferIPv4Stack=true would change nothing.
  2. Property/bean binding timing - NOT the cause. /actuator/env with
     show-values reports the endpoint correctly from systemEnvironment, and the
     sender demonstrably uses it: pointing it at a dead port (19411) fails the
     same way, and pointing it at the raw IP instead of the hostname also fails
     the same way. The value is right and it is being used.

DECISIVE CONTROL: a freshly constructed java.net.http.HttpClient, in the same
container, on a clean thread, POSTing to the same URL returns HTTP 202. The JDK
client, the network and the collector are all fine - only the long-lived client
inside the running application is broken.

WHERE TO GO NEXT:
  - ClosedChannelException on a fresh channel is the classic symptom of the
    calling thread carrying an interrupt flag: NIO auto-closes interruptible
    channels on interrupt. Find what interrupts AsyncReporter$Flusher, or what
    breaks the HttpClient's selector state. Note the app is otherwise healthy,
    so this is confined to the reporter's thread/client.
  - Practical workaround if the root trigger proves elusive: replace the
    transport. Boot lets a custom BytesMessageSender bean override
    ZipkinHttpClientSender - zipkin-sender-urlconnection or the OkHttp sender
    avoids the JDK HttpClient entirely, and HttpURLConnection is already proven
    to work in this exact container.
  - Worth checking whether Step 3's native run used the same sender; if it did,
    the trigger is environmental rather than a code difference.
Priority: HIGH - observability is a stated goal of the containerised stack, and
everything except span delivery is verified working.

----------------------------------------------------------------------------

Spring Boot project, on WebMVC since Step 1: use @SpringBootTest and @WebMvcTest

GOAL
Catch design-level errors that only surfaced under real usage - exactly like the
authorization defect found while investigating after Step 8, where a ROLE_USER
token on an ADMIN endpoint returned 500 instead of 403 because @PreAuthorize's
AuthorizationDeniedException was swallowed by GlobalExceptionHandler's
@ExceptionHandler(Exception.class) catch-all. Worth stressing: that bug was
PRE-EXISTING, not introduced by any step, and it survived undetected only because
every manual test token happened to carry ADMIN. Write tests for the whole CLASS
of defect, not the single instance.

COVERAGE SCOPE - five business services plus the gateway
  1. Happy path. CRUD per controller: create, read, update, delete, list with
     pagination. Assert status codes AND response shape.
     NOTE - correction to the original framing: there is no PagedResponseDTO in
     this codebase. Listing endpoints return Spring's Page<T>, and commons holds
     only PaginationInputDTO, SortInputDTO and PaginationUtil on the input side.
     Serialising Page<T> over JSON is itself historically fragile, so assert the
     concrete serialised shape rather than assuming it is stable.
  2. Authorization matrix. For EVERY @PreAuthorize endpoint: no token -> 401,
     wrong role -> 403, correct role -> reaches business logic. Systematically,
     across all endpoints, not only those already known to be protected. This is
     the Step 8 bug class.
  3. Exception handling. Every branch of GlobalExceptionHandler:
     MethodArgumentNotValidException, ConstraintViolationException, not-found,
     OptimisticLockException, DataAccessException, AccessDeniedException (the
     Step 8 fix) and the catch-all. Assert the exact status and ApiErrorDTO shape,
     not merely that a response came back.
  4. Feign behaviour. Four clients exist: AccountFeignClient, AlbumFeignClient,
     PhotoFeignClient, UserFeignClient. Known live paths include accounts ->
     users (UserFeignClient#isActive) and albums -> accounts
     (AccountFeignClient#findById) - both observed during Step 8. For each: the
     success path, a downstream 4xx decoded by CustomFeignErrorDecoder, and a
     downstream 5xx or unavailable producing the correct fallback. The fallbacks
     already exist and are worth asserting directly - isActiveFallback,
     findByUsernameAndActiveUserFallback, findAllFallback.
  5. Resilience4j. Circuit breaker transitions closed -> open -> half-open, retry
     behaviour, and fallbacks returning the expected shape and status rather than
     leaking a raw exception.
  6. Repository and persistence. For non-trivial query logic - filters,
     pagination, ownership-scoped queries - test against Testcontainers with
     MySQL rather than H2, so dialect differences cannot mask real bugs.
  7. MapStruct mappers. Step 5 proved ModelMapper had a silent field-name
     mismatch that returned null to the API for months. ReportingPolicy.ERROR now
     catches that at compile time, so mapper tests are the runtime safety net on
     top of the compile-time guarantee, not a substitute for it.

[2026-08-02 | platform decision] Use an OIDC provider for real projects, but design
against the protocol rather than the vendor
-----------------------------------------------------------------------------------
STRATEGIC / LONG-TERM. Not a defect, and NOT a plan to migrate
photo-app-authorization-service. That service stays exactly as it is: its value is
that it was built from scratch as a learning exercise. This records the decision
for the NEXT project and for the generic security library, so the reasoning is not
lost. Closely related to the PKCE item below.

DECISION (updated 2026-08-02): AWS COGNITO
The provider is AWS Cognito, deployed alongside ECS Fargate and intended to carry
through to PRODUCTION, not just local development. Chosen for this project and as
the default going forward, pending future business-model clarity.

Application code is still written against the OIDC/OAuth2 standard rather than
against Cognito. That principle is unchanged by the choice, for two reasons:

  1. Cognito's OIDC compliance has AWS-specific quirks worth insulating against.
     Ones to verify at implementation time, since Cognito's behaviour has shifted
     over the years:
       - access tokens historically carry no "aud" claim, using client_id instead,
         which breaks Spring's default audience validation. ID tokens do carry aud.
       - group membership arrives as "cognito:groups", not a standard claim, so the
         authorities mapping needs an explicit claim name.
       - the logout endpoint is /logout rather than a standard end_session_endpoint.
       - issuer-uri takes the form
         https://cognito-idp.{region}.amazonaws.com/{userPoolId}
     Each of these is a configuration or converter concern, and none should leak
     into the library.
  2. It keeps per-client provider swaps open. If an enterprise client later requires
     on-prem Keycloak, that becomes a configuration change rather than a rewrite.

The original decision text follows, and still holds - only the provider is now
settled.

ORIGINAL FRAMING
Adopt Keycloak - or any OIDC-compliant provider - as the default identity provider
for future projects handling real customer data, while writing all application code
against the OIDC/OAuth2 standard rather than against a specific provider.

WHY NOT KEEP THE CUSTOM IMPLEMENTATION
Authentication is one of the few areas where a subtle implementation error becomes
a direct security breach rather than a bug. Keycloak, Okta and Auth0 have absorbed
years of dedicated security review; a self-built issuer has not. The learning value
is real, the production risk is not worth taking.

THE MECHANISM FOR STAYING PROVIDER-AGNOSTIC
Every OIDC-compliant provider - Keycloak, Okta, Auth0, or a future custom server
built on Spring Authorization Server - exposes a standard issuer-uri and a JWKS
endpoint for public-key verification. Spring Security's oauth2-resource-server
consumes that natively:

    spring:
      security:
        oauth2:
          resourceserver:
            jwt:
              issuer-uri: https://your-provider.com/realms/your-app

From that one property Spring discovers the JWKS endpoint, fetches and caches the
public keys, and validates signature, expiry and issuer on every request. No custom
JWT parsing code at all.

WHY THIS IS A DIFFERENT SHAPE FROM WHAT EXISTS TODAY
The current setup signs with HS256 using a symmetric secret, so every service needs
the SAME shared secret in order to verify - which is also why photoapp.jwt.secret
is duplicated across seven config files today, and why decision 7 in the
dockerization plan kept that arrangement for the current round. Changing providers
under that model means replacing the mechanism outright.

With OIDC and JWKS the keys are asymmetric: only the identity provider holds the
private signing key, and each microservice needs nothing but the public key, fetched
automatically from the issuer-uri. Swapping providers becomes a configuration change
- the issuer-uri value, and possibly a claim name for roles - instead of a rewrite.
It also removes the current property that every service can MINT tokens, not merely
verify them.

IMPLICATION FOR THE FUTURE SECURITY LIBRARY (see PLATFORM-VISION.md)
Build it on Spring's standard JwtAuthenticationConverter and
JwtGrantedAuthoritiesConverter, mapping standard JWT claims onto CustomUserPrincipal.
No Keycloak-specific code anywhere inside the library. Only the issuer-uri and the
claim-name mappings are provider-specific, and those stay configuration - swappable
per environment or per client without touching how the services integrate with the
library.

NOT YET DECIDED - delivery and hosting model
Whether future client work runs in an own AWS account or in the client's own
infrastructure is an open BUSINESS question, deliberately out of scope for this
project's technical decisions. It is recorded here only because it is the thing
most likely to force a per-client provider swap, which is precisely what the
protocol-not-vendor principle above is there to absorb. Do not let it block
technical work; the design already tolerates either outcome.

Priority: strategic. Revisit when starting the next real project, or when
generalising photo-app-security-lib into the toolkit.

Note on the AWS backlog section of dockerization-plan.md: it lists "true OAuth2
PKCE flow" and "RSA/JWK signing with verify-only resource servers" as production
items. Both are subsumed by this decision - Cognito provides the authorization
server and the JWKS endpoint, so those entries should be read as "integrate with
Cognito", not as "build it".


[2026-08-02 | observation] PKCE flow is not a genuine PKCE implementation
--------------------------------------------------------------------------
KNOWN SIMPLIFICATION, NOT A BUG. PLATFORM-VISION.md already says the
authorization service "registers an in-memory PKCE client; it is a stepping
stone, not the product". Logged so it is not forgotten.

/auth/login accepts a codeVerifier directly in the login request body. That is a
JWT login with an extra field, not the PKCE authorization code flow, which
requires a client-generated code_verifier and derived code_challenge, a redirect
to an authorization endpoint, a temporary authorization code, and an exchange of
that code for a token using the original verifier.

VERIFIED IN THE CODE (2026-08-02), and it is thinner than the description above
suggests:
  - LoginRequestDTO declares codeVerifier with
    @NotBlank("Code verifier is required for PKCE"), so callers are FORCED to
    send one.
  - Nothing consumes it. Grepping the whole service for "odeVerifier" outside
    that DTO returns no hits. The value is required, then discarded - it is not
    hashed, compared, or stored. So the field is validation theatre rather than
    a partial implementation.
  - The service exposes /auth/login, /auth/refresh and /auth/revoke. There is no
    authorization endpoint at all, so no authorization code can ever be issued.
  - AuthorizationServerConfig registers a client with grant type
    AUTHORIZATION_CODE and redirect URI http://localhost:8080/callback, but
    nothing in the login path uses that RegisteredClientRepository. The config is
    inert. The redirect URI also points at localhost, which would not resolve
    correctly from inside a container.

CORRECT FIX: build the real authorization server on Spring Authorization Server,
per the platform vision. Do NOT patch the custom endpoint into something
PKCE-shaped piecemeal - that would entrench the stepping stone.

Small cleanup worth considering in the meantime, independent of that initiative:
either drop the unused codeVerifier field, or document it in place as a
placeholder. As it stands it requires every caller to send a value that is
ignored, which reads as a working PKCE check to anyone new to the code.

Priority: aligned with the future authorization-server initiative, not urgent for
the dockerization scope. See PLATFORM-VISION.md.


[2026-08-01 | Step 8] MEDIUM — endpoints are slow through the gateway in Docker
--------------------------------------------------------------------------------
Not blocking; the stack is functionally correct. Observed in Zipkin traces once
tracing started working:

    POST /auth/login    ~7.0s total at the gateway
                        ~6.3s of that inside photo-app-authorization-service
    GET  /users         3.2s total, listing 100 records
    GET  /accounts      4.828s total, 17 spans across 3 services
                        traceId 6a6ea8fed78d9418f5aff2b0ec6c6fd4

Far higher than expected for a local environment at this data volume. BCrypt's
deliberate cost factor could account for part of the login figure, but the
/users listing has no such excuse - it is a simple paginated read.

The /accounts trace confirms the problem is NOT confined to one service. Three
services and 17 spans for one request means the cost compounds per hop, so a
systemic per-hop overhead fits the evidence better than one slow component. That
strengthens starting point 1 below: resource contention would degrade every hop
at once, which is exactly the shape observed.

The fan-out is via Feign and is already identified from earlier work in this
session: accounts-service calls users-service through
UserFeignClient#isActive - visible in a Step 8 stack trace as
"Failure on isActive. The photo-app-users-service is not available" when
users-service was down. The third service in the trace is the gateway. So the
path is gateway -> accounts-service -> users-service.

Additional angle worth checking: whether any Feign calls in the accounts flow
are sequential where they could run in parallel. Look at AccountServiceImpl and
the Feign clients in photo-app-feign-lib. Note this is a code-shaped fix and the
latency may well be environmental - measure before restructuring anything,
otherwise it is optimising the wrong layer.

LIKELY ROOT CAUSE IDENTIFIED - Hibernate TRACE logging (evidence, not hypothesis)
In trace 6a6ea9c1ae30762e70012572db19d123 (albums-service) there is a ~1.8s gap
between "JWT validated successfully" at 02:21:54.842 and the first Hibernate
"binding parameter" line at 02:21:56.664, for a query that should take under
100ms. TRACE-level Hibernate logging emits one line per bound parameter per
query; every line is serialised to JSON and written to the shared log volume,
which plausibly accounts for multi-second latencies on any endpoint that touches
the database.

CONFIRMED CONFIGURATION - identical in all five service *-dev.properties:
    spring.jpa.show-sql=true
    spring.jpa.properties.hibernate.format_sql=true
    logging.level.org.hibernate.SQL=debug
    logging.level.org.hibernate.orm.jdbc.bind=trace
    logging.level.org.hibernate.type.descriptor.sql.BasicBinder=trace
So the TRACE levels are explicit, not inherited defaults. Three observations:
  - show-sql=true duplicates what org.hibernate.SQL=debug already logs; one of
    the two is redundant.
  - format_sql=true pretty-prints each statement across multiple lines, which
    multiplies the volume written per query on top of the per-parameter lines.
  - org.hibernate.type.descriptor.sql.BasicBinder is the Hibernate 5 binder
    logger. This project runs Hibernate 7.2.7, where it was replaced by
    org.hibernate.orm.jdbc.bind - which is also set. The BasicBinder line is
    therefore almost certainly dead config; verify, then delete it rather than
    just lowering it.

FIX APPLIED 2026-08-01 (config repo 719e5ee) - BUT IT DID NOT EXPLAIN THE NUMBERS
All four changes were made and verified live: org.hibernate.orm.jdbc.bind is now
WARN, show-sql and format_sql are gone, and the dead BasicBinder line is deleted.
org.hibernate.SQL stays at DEBUG and still works - a real request logs 2 SQL
statements, confirmed after the change.

The BasicBinder deletion was verified before removal, not assumed:
org/hibernate/type/descriptor/sql/BasicBinder.class is ABSENT from
hibernate-core-7.2.7.Final.jar. The class moved to
org.hibernate.type.descriptor.jdbc, so nothing could ever have logged under the
configured name.

MEASURED EFFECT - much smaller than the hypothesis predicted. A/B on the same
container, toggling the binder logger through the actuator, interleaved twice to
control for drift, 10 requests each, every response verified 200:

    bind=TRACE   avg 0.057s / 0.048s
    bind=WARN    avg 0.053s / 0.039s

A ~10-20% difference, inside the min/max spread - not a multi-second win. Log
volume tells the same story: 3 requests to /accounts produced 24 lines at TRACE
versus 18 at WARN, i.e. only 2 binder lines per request. That endpoint binds few
parameters (pagination limit and offset), so there was little noise to remove.
The hypothesis should hold better on endpoints that bind many parameters or that
issue N+1 queries - it was simply the wrong endpoint to test it against.

THE 4.828s FIGURE COULD NOT BE REPRODUCED AT ALL
GET /accounts in steady state runs at roughly 30-60ms, cold or warm, before and
after the change. The original 4.828s, 3.2s and 7s figures were almost certainly
FIRST-REQUEST-AFTER-STACK-START measurements, which fold in JIT warm-up, Eureka
registration propagation, gateway route and load-balancer resolution, Feign
client initialisation and connection-pool fill. That reframes the whole item:
there may be no steady-state latency problem, only an expensive first request.

WHAT TO DO NEXT
  - Re-measure deliberately: capture first-request-after-startup separately from
    steady state, for each endpoint. If only the first request is slow, this is a
    warm-up characteristic and not a defect.
  - If a steady-state problem does show up on other endpoints, starting point 1
    below (engine resources) remains the best lead.
  - The logging change is kept regardless: it removed redundant and dead
    configuration and reduces log volume, which is worth having on its own terms
    even though it was not the cause.

ORIGINAL PROPOSED FIX (now applied, retained for context):
Lower org.hibernate logging in the config repo's dev profile. Keep it granular
rather than switching Hibernate logging off: org.hibernate.SQL at DEBUG shows the
statement itself without every parameter bind and is cheap and useful. The
expensive parts are the per-parameter TRACE loggers and format_sql.

CONFIRM THE SCALE FIRST, in Kibana:
    logger_name:org.hibernate* AND traceId:"<any recent traceId>"
counts exactly how many log lines one request produces. Worth doing before and
after so the improvement is measured rather than assumed - and it also tells you
whether this fully explains the numbers or only part of them.

Note the interaction with starting point 1 below: heavy log writing and engine
resource contention would compound, so both may be contributing. Fixing the
logging is cheap and reversible, so do it first and re-measure before spending
time on engine tuning.

Investigation starting points:
  1. Docker Desktop resource allocation (CPU and RAM given to the engine).
     Fourteen containers run at once - eight application plus six infrastructure
     - so contention is plausible. Check the engine's limits before anything
     else, since everything below is downstream of it.
  2. JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=75" from the Step 6 Dockerfile.
     Compare the percentage against each container's actual memory limit and
     look for GC pressure; no per-container memory limits are set in
     docker-compose.yml, so the percentage resolves against whatever the engine
     exposes.
  3. HikariCP maximum-pool-size=5 from Step 4. Unlikely to bottleneck a single
     request, but worth ruling out under concurrent load later.
  4. Overhead from photo-app-tracing-lib (Step 8). Unlikely at this magnitude -
     URLConnectionSender reports asynchronously off the request thread.
     CAVEAT: comparing against a pre-fix trace is probably not possible. Zipkin
     runs with in-memory storage and its container was restarted several times
     during the Step 8 investigation, so no pre-fix traces should survive. A
     cleaner comparison is to run the same endpoints natively, where Step 3
     already showed working tracing, and diff the durations.

Useful extra signal for whoever picks this up: the same endpoints were exercised
natively in Steps 3 and 5 and did not feel slow, which points at the container
environment rather than at application code. Nothing was measured then, so that
is an impression rather than a baseline - capturing a native baseline first would
make the comparison meaningful.
Priority: MEDIUM.


[2026-08-01 | Step 8] Find what interrupts the Zipkin reporter thread
----------------------------------------------------------------------
Follow-up to the FIXED transport-swap item above. The swap restores
observability but only bypasses the defect; the JDK java.net.http.HttpClient is
still broken inside these containers and anything else that uses it would hit
the same wall.

What is established: the reporter fails with ClosedChannelException at
SocketChannelImpl.ensureOpen, i.e. the socket channel is already closed before
connect is attempted. That is the signature of a thread carrying an interrupt
flag, because NIO auto-closes interruptible channels on interrupt and never
reopens them. A freshly built client on a clean thread in the same container
returns 202 for the same request, so the JDK client itself is fine.

HYPOTHESIS FOR THE LOOSE END (why Step 3's native run worked but containers do
not) - NOT CONFIRMED, offered as a starting point:
  Virtual threads. spring.threads.virtual.enabled=true was added in Step 1 and
  may interact differently with NIO channel interruption under container CPU and
  memory constraints than in an unconstrained native JVM. A virtual thread that
  is unmounted, or carrier-thread pinning under CPU pressure, could plausibly
  leave an interrupt flag set on the thread performing the connect.
  Note the setting is currently on the GATEWAY only, while every service loses
  spans - so if virtual threads are the cause, the mechanism cannot be direct
  and that itself is informative. Check whether anything else enables virtual
  threads globally before pursuing this.

Suggested approach:
  - Reproduce with a minimal Boot app in a container, then bisect: with and
    without virtual threads, with and without CPU limits.
  - Instrument AsyncReporter$Flusher to log Thread.currentThread().isInterrupted()
    before each flush, which would confirm or kill the interrupt theory outright.
  - If confirmed, report upstream: this affects any Boot 4 application sending
    spans over the default sender in a container.
Priority: LOW-MEDIUM. Observability works via the URLConnection sender; this is
about the underlying defect, not the symptom.

[2026-08-01 | Step 2] Wrong/missing config-server credentials degrade silently
------------------------------------------------------------------------------
New failure mode introduced by putting HTTP Basic in front of the Config Server.
With spring.config.import=optional:configserver:..., a 401 is logged as a WARN
("Could not locate PropertySource ... 401") and startup CONTINUES with no remote
configuration at all. Whether the app then fails depends entirely on whether some
bean happens to need a property only the server provides — the gateway does fail,
because JwtClaimsParser requires ${photoapp.jwt.secret}, but that is luck, not a
guard. A component whose remote properties are all optional would boot silently
misconfigured.
Fix: drop the "optional:" prefix so a 401 or an unreachable server is fatal.
Already planned for containers via SPRING_CONFIG_IMPORT in Step 8; consider doing
the same for the packaged properties so native runs fail loudly too.
Priority: medium.

[2026-08-01 | Step 5] Audit remaining DTO/entity name mismatches
